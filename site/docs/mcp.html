AI integration

Drive Kata from an external AI agent (MCP)

Kata runs an MCP server that publishes its smell index and Fowler refactoring catalog as callable tools. Any MCP-compatible agent — Claude Code, Codex, Cursor, or a custom one you built — can list smells, request a refactor, and receive a unified diff, without touching your source files directly.

What you'll be able to do

  • List the tools Kata publishes over MCP and know what each one returns.
  • Point an MCP-compatible client at your running Kata instance.
  • Trace a full round-trip: agent asks for smells → Kata replies → agent picks one → Kata returns a diff → agent (or you) applies it.
  • Know what data crosses the MCP boundary and what stays local.

Transport

Kata's MCP server uses Streamable HTTP — the same transport Claude Code, Codex, and Cursor use as MCP clients — bound to 127.0.0.1 only. Nothing on the network can reach it; the CLI you configure must run on the same machine as Kata.

Kata picks a free port at startup and writes the endpoint URL to %LOCALAPPDATA%\Kata\mcp-endpoint.json. MCP clients that read that file (Claude Code, Codex, Cursor) discover Kata automatically.

Tools Kata publishes

The current tool surface is intentionally small — enough that an agent can find what to fix, ask Kata to fix it, and see the result. The full JSON Schema for each is served over the MCP list_tools handshake.

list_smells

Returns every 💩 badge currently on the diagram, with its category, severity, target symbol (fully qualified name + file/line), and the Fowler intent Kata would suggest.

get_smell_detail

Given a smell id from list_smells, returns the target symbol's source verbatim plus enough surrounding context (callers, callees, dependent types) to make a diff applyable.

list_refactorings

Returns the Fowler intents available on a given symbol — the same set that would appear in the right-click menu on that node. Preconditions are checked server-side, so an agent never gets Pull Up Method on a top-level class.

request_refactor

Given a target symbol and a Fowler intent name (plus any intent-specific parameters — a new name for Rename, a new class name for Extract Class, and so on), Kata executes the intent and returns a unified diff. Nothing is written to disk yet.

request_ai_diff

The MCP counterpart of the right-click Ask AI flow. The agent supplies a scoped prompt; Kata routes it through the AI CLI you configured in Preferences and returns the diff. This is how Cursor's own agent can drive Kata's AI diff loop.

apply_diff

Applies a unified diff (previously returned by request_refactor or request_ai_diff) to the working tree, and updates the diagram incrementally. Kata rechecks the policy and quality-delta banners before writing.

Auth

Kata's MCP server accepts local connections only. There is no bearer token because there is no network exposure — anyone able to reach 127.0.0.1 already has your user session. If that assumption breaks in your environment (shared machine, container namespaces), close Kata before stepping away.

Kata will refuse to start the MCP server if the machine is currently exposing 127.0.0.1 to a remote origin (SSH port-forward, some VPN configurations). If you rely on MCP for a headless workflow on such a machine, this is intentional; open an issue if you need a way around it.

Configure a client

Claude Code

Add Kata to ~/.config/claude-code/mcp.json: 

{
  "mcpServers": {
    "kata": {
      "type": "streamable-http",
      "endpointFile": "%LOCALAPPDATA%/Kata/mcp-endpoint.json"
    }
  }
}

Claude Code auto-discovers the port and reconnects when Kata restarts on a different one.

Codex CLI

Codex reads the same endpoint file. Add to ~/.codex/mcp.json: 

{
  "servers": [
    {
      "name": "kata",
      "transport": "streamable-http",
      "discover": "%LOCALAPPDATA%/Kata/mcp-endpoint.json"
    }
  ]
}

Cursor

In Cursor's settings, add an MCP server pointing at the endpoint file. Cursor's agent will list Kata's tools alongside its own, and its refactoring suggestions will route through request_refactor when Kata has a deterministic rewriter for the intent, falling back to request_ai_diff otherwise.

Custom / any MCP-compatible tool

Read the endpoint from the JSON file above and open a Streamable HTTP MCP connection. Any client that implements the MCP spec at protocol level will work — Kata's tool schemas are exposed through the standard list_tools handshake.

Example round-trip

A minimal agent script that finds the highest-severity smell, asks Kata for a deterministic refactor, and applies the resulting diff: 

const smells = await mcp.call("list_smells", { minSeverity: "warning" });
const top = smells.sort((a, b) => b.severity - a.severity)[0];

const options = await mcp.call("list_refactorings", { symbol: top.symbol });
const chosen = options.find(o => o.name === "Extract Method")
              ?? options[0];

const diff = await mcp.call("request_refactor", {
  symbol: top.symbol,
  intent: chosen.name,
  parameters: chosen.defaultParameters,
});

await mcp.call("apply_diff", { diff });

The whole loop lives outside Kata — Kata just answers questions and produces diffs.

What crosses the MCP boundary

  • The agent sees: the smell list, target symbols by FQN and file/line, the requested source snippets (only when it explicitly calls get_smell_detail or request_ai_diff), and the resulting diffs.
  • The agent does not see: Kata's internal type index, the full source tree, Preferences, or any file it did not explicitly request through the tool surface.
  • Kata never pushes data at the agent — every byte the agent receives is the result of a call it made.

Troubleshooting

Client can't find Kata's MCP endpoint

Confirm Kata is running and check that %LOCALAPPDATA%\Kata\mcp-endpoint.json exists. It is rewritten every time Kata starts; a stale file after a crash resolves to a dead port.

request_refactor returns "intent not applicable"

The intent's preconditions don't hold on the target symbol. Call list_refactorings for that symbol to see what is available.

apply_diff reports "diff no longer applies"

The source moved between the diff being generated and the apply call. Regenerate with a fresh request_refactor and try again.
